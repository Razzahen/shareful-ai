Use these annotated examples to calibrate quality when writing or reviewing a `SHARE.md` file. Each example explains what works and what doesn't.

## Good example: fix type

This share fixes Prisma N+1 queries. It demonstrates a well-structured fix with multiple solution options.

### Frontmatter

The frontmatter names the technology, describes the symptom, and uses the correct solution type.

```yaml
---
title: "Fix Prisma N+1 query problem with includes and joins"
slug: fix-prisma-n-plus-one-queries
tags: [prisma, database, performance, n-plus-one]
problem: "Prisma makes hundreds of individual queries when loading related data in a loop"
solution_type: fix
created: "2026-02-08"
environment:
  language: typescript
  framework: prisma
---
```

<Callout type="info">
**What makes this good:** The title starts with "Fix" matching `solution_type: fix`, names the technology (Prisma), and describes the specific problem (N+1). The problem field includes the observable symptom ("hundreds of individual queries"), making it searchable. Tags cover technology, domain, and pattern.
</Callout>

### Problem section

The Problem section shows a minimal reproduction with quantified impact.

```markdown
## Problem

Loading a list of records and then accessing their relations triggers one
additional query per record:

\`\`\`typescript
const posts = await prisma.post.findMany();
for (const post of posts) {
  const author = await prisma.user.findUnique({
    where: { id: post.authorId },
  });
}
\`\`\`

With 100 posts, this generates 101 database queries.
```

<Callout type="info">
**What makes this good:** Shows the broken code as a minimal reproduction, quantifies the impact ("101 database queries"), and does not explain the fix -- only the broken state.
</Callout>

### Solution section

The Solution section provides three labeled options with a recommended default.

```markdown
## Solution

**Option 1: Use `include` to eager-load relations (recommended)**

\`\`\`typescript
const posts = await prisma.post.findMany({
  include: { author: true },
});
\`\`\`

**Option 2: Use `select` for specific fields (better performance)**

\`\`\`typescript
const posts = await prisma.post.findMany({
  select: {
    id: true,
    title: true,
    author: { select: { name: true, email: true } },
  },
});
\`\`\`

**Option 3: Use `relationLoadStrategy: "join"` (Prisma 5.9+)**

\`\`\`typescript
const posts = await prisma.post.findMany({
  relationLoadStrategy: "join",
  include: { author: true },
});
\`\`\`
```

<Callout type="info">
**What makes this good:** Three clearly labeled options with a recommended default. Option 3 notes the version requirement in its label. Each code block has the `typescript` language label and is complete.
</Callout>

### Why It Works section

The share explains that Prisma does not load relations by default, that the N+1 arises from manual looping, and that `include` changes the behavior to use an `IN` clause. It also explains how `relationLoadStrategy: "join"` uses a SQL `JOIN` instead.

<Callout type="info">
**What makes this good:** Explains the root cause (default lazy behavior), not just "add include." Describes the actual SQL mechanism (`IN` clause vs `JOIN`). Written as prose, not code.
</Callout>

### Context section

The Context section lists version requirements, debugging tips, and related patterns.

```markdown
## Context

- Prisma 4.x+ for `include`, Prisma 5.9+ for `relationLoadStrategy: "join"`
- Use Prisma's query logging to detect N+1: `new PrismaClient({ log: ["query"] })`
- For GraphQL resolvers, consider `prisma-graphql-fields-optimizer` or DataLoader pattern
- `select` is more efficient than `include` when you don't need all columns
```

<Callout type="info">
**What makes this good:** Version requirements listed first. Includes a debugging tip (query logging) and related patterns (GraphQL). Formatted as a bulleted list where each bullet adds unique information.
</Callout>

## Good example: pattern type

This share demonstrates the TypeScript `satisfies` operator for type-safe config objects.

### Frontmatter

The frontmatter uses a title verb matching the pattern solution type and specifies the minimum TypeScript version.

```yaml
---
title: "Use TypeScript satisfies operator for type-safe config objects"
slug: fix-typescript-satisfies-type-safety
tags: [typescript, satisfies, type-safety, config]
problem: "Type annotation on config object widens types and loses literal inference"
solution_type: pattern
created: "2026-02-08"
environment:
  language: typescript
  version: "4.9+"
---
```

<Callout type="info">
**What makes this good:** Title starts with "Use" matching `solution_type: pattern`. The problem describes the technical symptom ("widens types and loses literal inference"). Version is quoted as `"4.9+"` (proper YAML for a value starting with a number).
</Callout>

The Problem section shows a concrete `Routes` type and demonstrates how a type annotation widens the inferred type. The Solution builds from simple (`satisfies` alone) to advanced (`satisfies` + `as const`), with comments showing the inferred types so readers can see the difference. The Why It Works section explains the mechanism in two focused paragraphs.

## Common mistakes

Avoid these patterns when writing shares.

### Bad frontmatter

This frontmatter violates multiple format rules at once.

```yaml
---
title: "fix stuff"
slug: Fix_Stuff
tags: [Fix, stuff, things, misc, general, code, programming, software, development, engineering, TypeScript]
problem: "broken"
solution_type: pattern
created: Feb 8
---
```

<Callout type="error">
**Problems:** Title is vague with no technology or symptom. Slug has uppercase and underscores (must match `/^[a-z0-9-]+$/`). Tags include uppercase, more than 10 items, and vague terms. Problem is a single word with no actual symptom. Solution type says `pattern` but the title says "fix." Date format is wrong (must be `YYYY-MM-DD`).
</Callout>

### Bad Problem section

This Problem section reads like a blog post instead of showing the broken state.

```markdown
## Problem

This is a common issue that many developers face when working with
modern web frameworks. There are several approaches to solving it,
and in this share I will walk you through the best one I found after
trying many different things.
```

<Callout type="error">
**Problems:** No code shown, no error message, no quantified impact. Reads like a blog introduction. Talks about the solution instead of showing the broken state.
</Callout>

### Bad Solution section

This Solution section is incomplete and lacks a language label.

````markdown
## Solution

Just add `include` to your query. This should fix it.

```
prisma.post.findMany({ include: { author: true } })
```
````

<Callout type="error">
**Problems:** Code block has no language label (should be `typescript`). Snippet is incomplete (no `await`, no `const`). Explanation mixed into solution text instead of code comments. Does not show the full working code.
</Callout>

### Bad Why It Works section

This section restates the solution instead of explaining the root cause.

```markdown
## Why It Works

It works because we added `include: { author: true }` to the query.
This tells Prisma to include the author in the results. See the
Prisma documentation for more information.
```

<Callout type="error">
**Problems:** Restates the solution ("we added include") instead of explaining the mechanism. Does not explain why `include` fixes the N+1 problem. Defers to external docs instead of explaining here.
</Callout>

### Bad Context section

This Context section is a paragraph that repeats the explanation instead of listing environment details.

```markdown
## Context

This solution uses Prisma's include feature to eager-load relations.
When you use include, Prisma will automatically join the related table
in the SQL query. This is much more efficient than loading each relation
individually. The include feature has been available since Prisma 2.0
and is the recommended approach for loading related data.
```

<Callout type="error">
**Problems:** Written as a paragraph instead of a bulleted list. Repeats the solution explanation (belongs in Why It Works). No specific version numbers, no gotchas, no related tools.
</Callout>

## Quality checklist

Run through this checklist before publishing a share:

**Frontmatter:**
- Title starts with a verb matching `solution_type` (Fix, Use, Configure)
- Title is specific (names technology and problem), under 128 characters
- Slug matches the parent directory name, lowercase with hyphens only, under 64 characters
- Tags are 1-10 items, all lowercase, each under 32 characters
- Problem field includes the error message or observable symptom, under 256 characters
- `solution_type` matches the title verb and content
- `created` is `YYYY-MM-DD` format

**Problem section:**
- Shows broken code with a minimal reproduction
- Includes exact error message or quantified impact
- Does not explain the fix

**Solution section:**
- All code blocks have language labels
- Code is complete and runnable (not fragments)
- Multiple options are labeled with "(recommended)" on the default

**Why It Works section:**
- Explains the root cause, not just restates the fix
- Written as prose (1-3 paragraphs)
- Covers why the default behavior causes the problem

**Context section:**
- Formatted as a bulleted list
- Version requirements listed first
- Includes at least one gotcha or limitation

**Overall:**
- Body is under 300 lines
- All four required sections present in order
- No placeholder content
